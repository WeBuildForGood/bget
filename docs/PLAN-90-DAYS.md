# BGET — 90-Day Plan

Assumes: you have a Discord server, 2–3 interested developers, and no brand assets yet.

**The whole plan comes down to one sentence:**
*Ten excellent people, one weekly ritual, and no unanswered introductions.*

---

## Phase 1 — Foundation (Days 1–14)

### Week 1: Build the room
- [ ] Create `/workspace/BGET` docs (done) — read MANIFESTO, VALUES, MEMBERSHIP, DISCORD
- [ ] Rewrite `#manifesto`, `#rules`, `#introductions` in your server using them
- [ ] Restructure Discord per [DISCORD.md](DISCORD.md): create the 6 categories
- [ ] Set roles: `@Seedling` for your existing 2–3 people, `@Steward` for you
- [ ] Enable Membership Screening with the short values form
- [ ] Archive old channels (don't delete)
- [ ] Secure handles: domain + GitHub org + Discord vanity (even unused)

### Week 2: First ritual + first recruits
- [ ] **Run Build Night #1** — invite the existing 2–3. Small is fine. *Ship something, even a README.*
- [ ] Personally invite **2 people** you've actually worked with ([invite template](templates/invite-message.md))
- [ ] Reply to every introduction personally, within 24h
- [ ] Post the first `#deep-discussions` Think prompt
- [ ] Start a simple tracker ([template](templates/roster.md)) — name, join date, trial status, notes

**Phase 1 exit:** ≥ 4 people, Build Night ran once, zero unanswered intros.

---

## Phase 2 — The First Ten (Days 15–45)

### Week 3–4
- [ ] Recruit **1–2 people per week**, conversation required
- [ ] Build Night weekly, non-negotiable — even if 3 people show
- [ ] Your existing members host one thread each this week (start rotating ownership early)
- [ ] Add `#goals` and `#accountability` — you post yours first, publicly
- [ ] Run the first **Deep Dive Lite** (10 min, no slides, you host)

### Week 5–6
- [ ] Reach and confirm **10 members** through trial
- [ ] Host the first **BGET Challenge** (teams of 2–4, one week, simple prompt)
- [ ] Publish the first `#impact-reports` item — even something small and real
- [ ] Enable the **one referral slot per quarter** rule
- [ ] Appoint your first **2 Stewards** from demonstrated behaviour

**Phase 2 exit:** 10 confirmed members, ≥6 active weekly, 2 people besides you hosting.

> **Do not proceed to Phase 3 until this holds.** Recruiting to 50 with 10
> disengaged people teaches your community that showing up is optional.

---

## Phase 3 — Prove the system (Days 46–75)

- [ ] Full rhythm live: Build Night + Deep Dive + Think + Challenge + Impact
- [ ] **First member-led Impact day** (physical, measured, photographed)
- [ ] Write the mod playbook from real incidents, not theory
- [ ] First **Showcase** — every active project demos, post publicly
- [ ] Publish the charter v1 and run the first member feedback thread
- [ ] Recruit members **51–70** via referrals only
- [ ] Start a public build log / blog: Deep Dive notes + Impact reports
- [ ] Run the Problem Commons loop **manually, twice** — take a real problem from
      inside the community, frame it, form a small team, see it through
      ([PROBLEM-COMMONS.md](PROBLEM-COMMONS.md) Phase A). Prove the process
      before publishing any intake.

**Phase 3 exit:** a week where you're offline and the server still runs;
members referencing your values without you present.

---

## Phase 4 — Prepare to scale (Days 76–90)

- [ ] **Unlock `🔒 BGET LABS`** — first real project teams form
- [ ] Define Labs project standards (purpose, lead, board, definition of done)
- [ ] Add one automation: welcome DM, trial check-in, or application routing
- [ ] Cohort admissions begin: next 10–15 people admitted *together*
- [ ] Open the sponsorship conversation with one company whose engineers you'd want
- [ ] Publish quarterly transparency note (even at $0 — the habit matters)
- [ ] **Publish the Problem Commons** — structured intake live
      ([template](templates/problem-submission.md)), 2–3 framed problems on
      display, honest promise: *every submission answered within 72h*
      (Phase B — see [PROBLEM-COMMONS.md](PROBLEM-COMMONS.md) §12)
- [ ] Ship the founder note + people section on the website ([PEOPLE.md](PEOPLE.md))
- [ ] **Retrospective:** what actually worked? Write it down. Kill what didn't.

**90-day success:**
- 25–50 members, quality-filtered, most active
- 3+ events run per week without you doing all of them
- ≥1 Labs project with a real lead and shipped output
- Problem Commons intake open and honest — zero submissions waiting >72h
- Zero unanswered introductions, ever
- A charter members have actually amended at least once

---

## What to measure weekly (5 minutes, in `roster.md`)

| Metric | Target |
|--------|--------|
| Active members (posted/contributed this week) | ≥ 50% of roster |
| Build Night attendance | ≥ 4 |
| Unanswered intros > 24h | 0 |
| Events held vs planned | 100% |
| Member-initiated threads/activities | ≥ 3 |
| Applications waiting > 72h | 0 |
| Problem submissions waiting > 72h | 0 |
| You personally doing everything | ↓ each week |

*Problem metrics only start counting once intake opens (Phase 4) — until then
they're trivially zero, which is honest but not an achievement.*

---

## The three things that matter most

1. **Run Build Night every week.** Consistency is the whole game.
2. **Answer every introduction.** Within 24 hours, personally. This is the
   single highest-leverage act in community building.
3. **Guard the first ten.** Everything after this is easier if these ten are
   the right people — and much, much harder if they aren't.

The plan is not the hard part. The hard part is doing the boring weekly thing
on the weeks when nobody shows up. Those are the weeks that decide whether
BGET exists in a year.
